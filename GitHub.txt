Build a production-ready, mobile-first web application called Zip2Git.

Zip2Git is a minimalist web tool that lets users select a ZIP file from their phone or computer and synchronize its project files with an existing GitHub repository and branch.

The core purpose is:

ZIP → Extract → Compare → Preview Changes → Sync → GitHub

The website must be focused on one task only. Do not build a dashboard, account system, cloud storage, or unnecessary features.

Core Requirements

Build the website as a modern responsive web application.

Recommended stack:

- React
- TypeScript
- Vite
- Modern CSS or Tailwind CSS
- GitHub REST API
- Browser File System APIs where appropriate
- JSZip or an equivalent browser-compatible ZIP library

The website must work without a custom backend.

All ZIP processing must happen locally in the user's browser.

GitHub API requests must be made directly from the browser over HTTPS.

Do not create or require a custom server, database, Firebase Functions, Supabase backend, or external API proxy for the core functionality.

Main User Flow

The complete user flow should be:

1. Open Zip2Git.
2. Enter GitHub repository URL.
3. Enter branch name.
4. Enter GitHub Personal Access Token.
5. Enter commit message.
6. Select a ZIP file.
7. Process the ZIP locally.
8. Validate the repository and branch.
9. Read the existing repository tree.
10. Compare ZIP contents with the repository.
11. Show a change preview.
12. User confirms synchronization.
13. Create the required Git objects/commit using GitHub's API.
14. Update the selected branch.
15. Show the successful commit.
16. Allow the user to open the commit on GitHub.

ZIP Processing

Process the ZIP completely in the browser.

Do not upload the original ZIP to a server.

Use a reliable browser ZIP library such as JSZip.

Extract files into memory or browser-managed temporary structures.

Do not write extracted files to a public server.

Preserve relative paths.

Example ZIP:

app/
src/
build.gradle
settings.gradle

must be synchronized to:

repository root/app/
repository root/src/
repository root/build.gradle
repository root/settings.gradle

ZIP Security

Treat ZIP files as untrusted input.

Protect against ZIP Slip/path traversal.

Reject paths containing:

../

Reject absolute paths.

Normalize paths before processing.

Never allow extracted files to escape the application's intended temporary processing area.

Reject invalid paths.

Set reasonable limits for:

- total uncompressed size
- number of files
- individual file size

Show a clear error if limits are exceeded.

Never execute files from the ZIP.

Special Git Directory Handling

If the ZIP contains:

.git/

do not synchronize the ".git" directory.

Git metadata from the ZIP must never overwrite the repository's actual Git metadata.

The app should also ignore other unsafe filesystem metadata.

Root Folder Detection

Handle common ZIP structures intelligently.

Example:

project/
app/
src/
build.gradle

If the ZIP was clearly created by compressing the project folder itself, detect the outer folder and avoid unnecessarily creating:

repository/project/app/

when the intended result is:

repository/app/

If the ZIP contains multiple meaningful top-level files/folders, preserve the structure.

When automatic detection is ambiguous, show a simple root selection step.

Example:

○ ZIP root

GitHub Validation

Before making any changes:

1. Validate repository URL.
2. Verify repository exists.
3. Verify token authentication.
4. Verify token has permission to modify the repository.
5. Verify the selected branch exists.
6. Read the current branch commit.
7. Read the current Git tree.

If validation fails, do not modify anything.

GitHub Sync Behavior

This is the most important part of the application.

Zip2Git must behave like a project synchronization tool.

The target state is:

GitHub repository tree = ZIP project tree

For each file:

Added

File exists in ZIP but not in GitHub.

Action:

Add file.

Modified

File exists in both places but the contents differ.

Action:

Update file.

Unchanged

File exists in both places and contents are identical.

Action:

Do nothing.

Deleted

File exists in GitHub but is not present in the ZIP.

Action:

Delete it.

This means if the user uploads a newer version of their project, files removed from the new ZIP should also be removed from the selected repository branch.

Do not leave obsolete project files behind.

Important Scope Rule

For the first version, the ZIP represents the entire repository root.

Therefore:

If a file is absent from the ZIP, it is considered removed and should be deleted from the repository.

However, protect important GitHub repository metadata where necessary.

Do not delete:

.git

GitHub's internal Git metadata is never directly manipulated as a normal project file.

Change Comparison

Compare actual file contents.

Do not rely only on filenames.

For text files, binary files, images, fonts, archives, etc., preserve the original bytes.

Do not alter:

- encoding
- line endings
- binary contents

unless explicitly required by GitHub's API format.

Calculate hashes locally where useful to avoid unnecessary updates.

GitHub Commit Implementation

Use GitHub's official Git database REST API where appropriate.

Prefer an efficient tree/blob/commit workflow rather than creating one commit per file.

Preferred workflow:

1. Get current branch reference.
2. Get current commit.
3. Get current tree.
4. Compare current repository tree with ZIP.
5. Create blobs for new/modified files.
6. Build the new Git tree.
7. Represent deleted files appropriately.
8. Create one new commit.
9. Set the selected branch reference to the new commit.
10. Verify the branch update.

The result should normally be one logical synchronization commit.

Do not rewrite Git history.

Previous commits must remain available.

Large Repository Handling

Design the implementation to handle reasonably large repositories.

Do not blindly download unnecessary file contents.

Use Git tree information to determine which files need to be fetched.

Only retrieve existing file contents when needed for comparison.

Be aware of GitHub REST API response and file-size limitations.

If a file cannot safely be synchronized through the selected API method, show a clear error instead of silently corrupting it.

Repository Race Protection

Prevent accidental overwrites if the repository changes during synchronization.

The process should remember the branch's starting commit SHA.

Before updating the branch, verify that the branch still points to the same expected commit.

If it has changed:

Do not overwrite the new remote commit.

Show:

Repository changed while syncing

No changes were pushed. Please sync again.

Token Handling

The PAT is highly sensitive.

Never:

- store it permanently
- put it in localStorage
- put it in sessionStorage
- put it in IndexedDB
- put it in cookies
- put it in URL parameters
- send it to analytics
- send it to your own server
- print it in console logs
- include it in crash reports

Only use it for direct GitHub API requests.

Clear the runtime reference after:

- successful sync
- failed sync
- cancellation
- leaving the workflow where appropriate

The UI must never display the complete token.
